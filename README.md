# Medicam Server

FastAPI backend и BLE-провижининг для камеры Medicam на Radxa.

## Подключение устройства

1. Ненастроенная камера постоянно публикует BLE-сервис с именем
   `Medicam-XXXXXX`.
2. Приложение отправляет по BLE команду `SCAN_WIFI`, затем `CONNECT_WIFI`.
3. После успешного подключения камера создаёт API-токен и возвращает его
   приложению вместе с IP-адресом и идентификатором устройства.
4. Приложение проверяет токен через HTTP и дальше использует заголовок
   `X-Medicam-Token` для защищённых маршрутов.

BLE также включается автоматически, если Wi-Fi потерян. После физической
перезагрузки уже настроенной камеры действует пятиминутное окно восстановления —
это позволяет вернуть доступ после переустановки приложения. Авторизованный
владелец может открыть окно на 10 минут через
`POST /provision/recovery/start`.

## Сервисы

- `medicam.service` — HTTP API;
- `medicam-ble.service` — BLE GATT-сервис;
- `medicam-ble-manager.service` — включает BLE только для настройки,
  восстановления или при потере Wi-Fi.

Установка/обновление BLE-сервисов:

```bash
./scripts/install_ble_services.sh
```

## Проверка

```bash
medicam-venv/bin/python -m unittest discover -s tests -v
```

## Запись звука

На Linux камера пишет FullHD-видео 30 fps как исходный MJPEG-поток без
перекодирования. Одновременно ALSA сохраняет звук в raw PCM (48 кГц, mono).
После `POST /stop` FFmpeg копирует видеопоток без изменений, кодирует только
звук в AAC 128 кбит/с и синхронизирует начало дорожек. Аудиоинтерфейс открывается
перед UVC-видео, что требуется совмещённой USB-камерой; короткий опережающий
фрагмент звука автоматически отрезается. PCM временно хранится в `/run/medicam`,
чтобы запись FullHD MJPEG на microSD не вызывала переполнение аудиобуфера.
Файлом владеет сервер, поэтому даже аварийный USB-disconnect не удаляет уже
записанный звук и прерванную запись можно финализировать обычным `POST /stop`.
Такой процесс не создаёт дополнительной нагрузки на видеозахват во время
съёмки.

- `GET /audio/devices` — список доступных ALSA-входов и выбранный микрофон;
- `POST /audio/test` — короткая проверка уровня сигнала и перегруза;
- `POST /settings` с `audio_enabled` и `audio_device` — настройка записи;
- `GET /recording/status` — полное состояние записи: фаза, активность камеры и
  микрофона, файл, длительность, текущий размер, свободное место, доступность
  камеры и последняя структурированная ошибка.

Рекомендуемое значение `audio_device=auto`: после подключения USB-микрофона
оно не зависит от номера `/dev/snd/*`. Конкретный вход можно закрепить по его
стабильному ALSA ID, например `plughw:CARD=HD,DEV=0`.

`scripts/install_server_runtime.sh` устанавливает systemd drop-in с
`RuntimeDirectory=medicam` и `RuntimeDirectoryPreserve=restart`.
`/update/apply` запускает его автоматически перед перезапуском backend. PCM в
RAM поэтому переживает рестарт сервиса; после полного отключения питания raw
MJPEG всё равно восстанавливается в MP4, но без утраченного RAM-аудио.

## Надёжность записи

Во время записи сервер атомарно поддерживает
`videos/.recording-state.json`. Watchdog отслеживает неожиданный выход UVC и
ALSA, останавливает оставшийся процесс и переводит запись в `interrupted`.
Повторный `POST /start` не создаёт второй процесс, а `POST /stop` безопасно
повторяется: незавершённый raw-файл собирается в MP4. Если аудио повреждено,
сервер повторяет восстановление без звука; при неудаче raw и PCM не удаляются.
После успешной сборки `ffprobe` возвращает в ответе `quality`: фактические и
ожидаемые кадры, длительность, средний FPS и итоговый признак `healthy`.

OTA-обновление отклоняется с HTTP 409 во время записи или восстановления,
чтобы штатное обновление не обрывало съёмку.

Автоматический аппаратный прогон использует именно HTTP-роуты и отдельно
проверяет каждый MP4 через `ffprobe`:

```bash
./scripts/test_recording_long_run.py --durations 60,600,1800
```

По умолчанию создаётся `recording-long-run-report.json` с результатами для
1, 10 и 30 минут: expected/actual frames, avg FPS, длительность, разрешение и
доля доставленных кадров. Тест считается успешным при FullHD, avg FPS не ниже
29.5 и доставке не менее 99.5% ожидаемых кадров.

API запускается на порту `8000`. Публичными остаются только обнаружение и
обезличенный статус; управление камерой требует токен.
