# Medicam Server

FastAPI backend и BLE-провижининг для камеры Medicam на Radxa.

## Подключение устройства

1. Ненастроенная камера постоянно публикует BLE-сервис с именем
   `Medicam-XXXXXX`.
2. Приложение отправляет по BLE команду `SCAN_WIFI`, затем `CONNECT_WIFI`.
3. После успешного подключения камера создаёт API-токен и возвращает его
   приложению вместе с IP-адресом и идентификатором устройства.
4. Приложение проверяет токен через HTTP и дальше использует заголовок
   `X-Medicam-Token` для защищённых маршрутов.

BLE также включается автоматически, если Wi-Fi потерян. После физической
перезагрузки уже настроенной камеры действует пятиминутное окно восстановления —
это позволяет вернуть доступ после переустановки приложения. Авторизованный
владелец может открыть окно на 10 минут через
`POST /provision/recovery/start`.

## Сервисы

- `medicam.service` — HTTP API;
- `medicam-ble.service` — BLE GATT-сервис;
- `medicam-ble-manager.service` — включает BLE только для настройки,
  восстановления или при потере Wi-Fi.

Установка/обновление BLE-сервисов:

```bash
./scripts/install_ble_services.sh
```

## Подписанные OTA-обновления

`GET /version` возвращает commit и release backend, версии app/BLE-протоколов,
версию образа Radxa, ревизию USB-камеры и uptime. `/ping` также содержит полный
commit для независимого post-restart healthcheck.

Устройство больше не обновляется с `origin/main`. `GET /update/check` видит
только стабильные теги `medicam-vMAJOR.MINOR.PATCH`, подписанные выделенным
Ed25519 OTA-ключом. Подпись одновременно подтверждает hash commit. Неподписанные
и повреждённые теги игнорируются, downgrade запрещён root-owned trust state.

`POST /update/apply` запускает фоновую установку, а `GET /update/status`
возвращает состояние и прогресс: download, signature verification, install,
restart, healthcheck и rollback. Внешний root-owned активатор ждёт новый backend
60 секунд; при ошибке автоматически восстанавливает предыдущий commit,
зависимости и systemd units. Причина сохраняется и показывается приложением.

Release-процесс и хранение ключа описаны в
[`docs/ota-release.md`](docs/ota-release.md). Подписанный тег создаётся командой:

```bash
./scripts/create_ota_release.sh 1.0.0
```

## Запись звука

На Linux камера пишет FullHD-видео 30 fps как исходный MJPEG-поток без
перекодирования. Одновременно ALSA сохраняет звук в raw PCM (48 кГц, mono).
После `POST /stop` FFmpeg копирует видеопоток без изменений, кодирует только
звук в AAC 128 кбит/с и синхронизирует начало дорожек. Аудиоинтерфейс открывается
перед UVC-видео, что требуется совмещённой USB-камерой; короткий опережающий
фрагмент звука автоматически отрезается. PCM временно хранится в `/run/medicam`,
чтобы запись FullHD MJPEG на microSD не вызывала переполнение аудиобуфера.
Файлом владеет сервер, поэтому даже аварийный USB-disconnect не удаляет уже
записанный звук и прерванную запись можно финализировать обычным `POST /stop`.
Такой процесс не создаёт дополнительной нагрузки на видеозахват во время
съёмки.

- `GET /audio/devices` — список доступных ALSA-входов и выбранный микрофон;
- `POST /audio/test` — короткая проверка уровня сигнала и перегруза;
- `POST /settings` с `audio_enabled` и `audio_device` — настройка записи;
- `GET /recording/status` — полное состояние записи: фаза, активность камеры и
  микрофона, файл, длительность, текущий размер, свободное место, доступность
  камеры и последняя структурированная ошибка.

Рекомендуемое значение `audio_device=auto`: после подключения USB-микрофона
оно не зависит от номера `/dev/snd/*`. Конкретный вход можно закрепить по его
стабильному ALSA ID, например `plughw:CARD=HD,DEV=0`.

`scripts/install_server_runtime.sh` устанавливает первоначальный systemd
runtime и независимый OTA-активатор. Дальше signed activator синхронизирует
drop-in с `RuntimeDirectory=medicam` и `RuntimeDirectoryPreserve=restart` при
каждом релизе или rollback. PCM в RAM поэтому переживает рестарт сервиса; после
полного отключения питания raw MJPEG всё равно восстанавливается в MP4, но без
утраченного RAM-аудио.

## Надёжность записи

Во время записи сервер атомарно поддерживает
`videos/.recording-state.json`. Watchdog отслеживает неожиданный выход UVC и
ALSA, останавливает оставшийся процесс и переводит запись в `interrupted`.
Повторный `POST /start` не создаёт второй процесс, а `POST /stop` безопасно
повторяется: незавершённый raw-файл собирается в MP4. Если аудио повреждено,
сервер повторяет восстановление без звука; при неудаче raw и PCM не удаляются.
После успешной сборки `ffprobe` возвращает в ответе `quality`: фактические и
ожидаемые кадры, длительность, средний FPS и итоговый признак `healthy`.
Для MP4 используется точный контейнерный `nb_frames`, который читается за
секунды даже у длинной записи; если контейнер не содержит счётчик, сервер
автоматически выполняет полный `-count_frames`.
Timeout финализации и полного `ffprobe` рассчитывается по размеру raw-файла,
поэтому 10- и 30-минутные записи не обрываются по короткому лимиту.

OTA-обновление отклоняется с HTTP 409 во время активного захвата или
финализации, чтобы штатное обновление не обрывало съёмку. Для уже прерванного,
но сохранённого raw OTA разрешено — это позволяет установить исправление и
затем повторить безопасное восстановление.

Автоматический аппаратный прогон использует именно HTTP-роуты и отдельно
проверяет каждый MP4 через `ffprobe`:

```bash
./scripts/test_recording_long_run.py --durations 60,600,1800
```

По умолчанию создаётся `recording-long-run-report.json` с результатами для
1, 10 и 30 минут: expected/actual frames, avg FPS, длительность, разрешение и
доля доставленных кадров. Тест считается успешным при FullHD, avg FPS не ниже
29.5 и доставке не менее 99.5% ожидаемых кадров.

API запускается на порту `8000`. Публичными остаются только обнаружение и
обезличенный статус; управление камерой требует токен.

## Медиатека

`GET /videos` возвращает быстрый постраничный список. Параметры `page`,
`page_size`, `sort`, `order` и `refresh` позволяют приложению загружать записи
частями, менять сортировку и выполнять pull-to-refresh. Базовые данные файла
возвращаются сразу, а поле `metadata_status=loading` сообщает, что `ffprobe` и
превью ещё готовятся в фоновой задаче. Готовые данные и JPEG-превью хранятся в
атомарном индексе `videos/.media-index.json` и переживают перезапуск backend.

- `GET /videos/{filename}/thumbnail` — авторизованное JPEG-превью;
- `GET /videos/{filename}` — потоковый просмотр с HTTP byte ranges;
- `GET /download/{filename}` — потоковое скачивание оригинального MP4;
- `DELETE /delete/{filename}` — удалить одну запись;
- `POST /videos/delete` с JSON `{"filenames": [...]}` — удалить до 100 записей;
- `DELETE /videos/clear` — очистить медиатеку.

## Управление хранилищем

`GET /storage` возвращает объём накопителя и медиатеки, десять крупнейших
роликов, пороги предупреждения/блокировки и консервативную оценку оставшегося
времени FullHD/30. Оценка использует фактический битрейт готовых роликов и
учитывает двойной объём, необходимый для безопасной сборки MP4 из MJPEG.

Политика автоочистки сохраняется атомарно через `POST /storage/policy`:

- `{"mode":"off"}` — не удалять автоматически;
- `{"mode":"low_space"}` — удалять старые ролики до безопасного остатка;
- `{"mode":"keep_last_gb","value":20}` — хранить последние 20 GB;
- `{"mode":"keep_last_days","value":30}` — хранить последние 30 дней.

`POST /storage/cleanup` с `{"reclaim_gb":5}` вручную освобождает указанный
объём, начиная с самых старых завершённых MP4. Любая очистка запрещена во время
записи. При старте применяется выбранная политика, а при критическом остатке
запись не запускается. Watchdog останавливает текущий захват до исчерпания
резерва, поэтому заполнение карты не повреждает сервис и оставляет место для
финализации.

Удаление блокируется во время записи и финализации с кодом
`recording_in_progress`: это защищает захват кадров от конкурирующей дисковой
нагрузки и исключает гонку с создаваемым MP4.

## Диагностика и поддержка

Все диагностические маршруты требуют действующий `X-Medicam-Token`:

- `GET /diagnostics/health` — единый снимок Wi-Fi/IP, накопителя, камеры,
  микрофона, записи, backend/BLE/OTA, systemd-служб, температуры и USB-цепочки;
- `POST /diagnostics/self-test` — 30 кадров FullHD/30 без добавления ролика в
  медиатеку, секундный тест микрофона, запись/чтение/fsync накопителя и проверка
  локальной сети/шлюза;
- `GET /diagnostics/bundle` — потоковый ZIP с health и ограниченными хвостами
  backend, FFmpeg, BLE и OTA-журналов.

Self-test и старт записи используют общий аппаратный lock: UVC/ALSA никогда не
открываются двумя операциями одновременно. Тестовый MJPEG и файл проверки
накопителя всегда удаляются; последний результат атомарно сохраняется в
`/var/lib/medicam/last-self-test.json` с режимом `0600`.

Перед упаковкой архива сервер рекурсивно скрывает SSID, удаляет текущие и
помеченные старые API-токены, пароли, PSK, pairing secrets, заголовки
Authorization и любые PEM private keys. На каждый источник журнала действует
лимит 512 KiB, архив не сохраняется на Radxa.

Signed OTA устанавливает `deploy/udev/99-medicam-usb-power.rules`: для камеры
`eba4:6579` и поддерживаемого VIA-хаба `2109:2817/0817` выставляется
`power/control=on`. Это исключает runtime autosuspend как программную причину
одновременного исчезновения UVC и USB Audio. Диагностика показывает фактическую
скорость USB, цепочку хаба, режим питания и найденные в `ffmpeg.log` ошибки
отключения. Для коммерческого устройства всё равно предпочтителен короткий
прямой OTG-адаптер либо качественный хаб с отдельным питанием.
